# FindIT - Architecture and design

This document explains how the system is built, why the important decisions were made and
how the requirements of the PRD are traced to the implementation.

---

## 1. System overview

```
                    ┌──────────────────────────────────────────────┐
   Browser          │  Spring Boot application (single artifact)    │
  (HTML/CSS/JS  ───►│  ┌──────────────┐   ┌────────────────────┐  │ ───► Azure SQL
   + Bootstrap)     │  │ Controllers  │──►│ Services           │  │ ───► Database
                    │  │ (REST)       │   │ (business rules)   │  │      (private)
                    │  └──────────────┘   └─────────┬──────────┘  │ ───► Azure Blob
                    │  ┌──────────────┐             │             │      Storage
                    │  │ Spring       │             ▼             │      (private)
                    │  │ Security     │      ┌─────────────┐      │
                    │  │ (session,    │      │ Repositories │      │
                    │  │  CSRF, roles)│      └─────────────┘      │
                    │  └──────────────┘                           │
                    │  ┌──────────────┐   ┌────────────────────┐  │
                    │  │ Front end    │   │ ImageStorage       │  │
                    │  │ (static/)    │   │ local | azure blob │  │
                    │  └──────────────┘   └────────────────────┘  │
                    └──────────────────────────────────────────────┘
```

The front end is packaged into the same jar as the API (`classpath:/static`). One process
serves the UI and the API, so there is no CORS configuration in the default setup and a
single Azure App Service deployment is enough.

## 2. Layers

| Package | Responsibility |
| --- | --- |
| `config` | Spring configuration: security filter chain, web/CORS, configuration properties, local seed data |
| `controller` | HTTP concerns only: mapping, validation of the request body, DTO conversion |
| `service` | Business rules: report lifecycle, claims, matching, moderation, audit |
| `repository` | Spring Data JPA repositories and specifications for the dynamic search |
| `domain` | JPA entities and enums |
| `dto` | Request and response records (never entities) |
| `exception` | `ApiException` hierarchy and the central JSON error handler |
| `security` | Principal, authentication handlers, CSRF cookie filter, rate limiter |
| `storage` | `ImageStorage` interface with a local and an Azure Blob implementation |

**Rule:** controllers never decide permissions or status transitions. They call a service
method, and the service decides. Every protected route is additionally guarded by the
Spring Security route rules, so a mistake in one layer does not open the data.

```

 location_id  -> locations               status (PENDING|APPROVED|REJECTED|WITHDRAWN)

         RETURNED|CLOSED|REJECTED)        review_reason

audit_logs

```

* All identifiers are generated by the database (`IDENTITY`).
* All timestamps are stored in UTC.
* Foreign keys and unique constraints are enforced by the database; the frequently filtered
  columns (`type`, `status`, `category_id`, `location_id`, `event_date`, `created_by`,
  `created_at`) are indexed.
* The schema is created and migrated exclusively by Flyway. Hibernate never changes it
  (`ddl-auto: none` in Azure, `validate` locally).

### Migration portability (H2 and Azure SQL)

One migration file serves both databases. Dialect specific parts are placeholders that are
resolved per profile:

| Placeholder | Local (H2) | Azure (SQL Server) |
| --- | --- | --- |
| `${id_identity}` | `GENERATED BY DEFAULT AS IDENTITY` | `IDENTITY(1,1)` |
| `${boolean_type}` | `BOOLEAN` | `BIT` |
| `${bool_true}` / `${bool_false}` | `TRUE` / `FALSE` | `1` / `0` |
| `${datetime_type}` | `TIMESTAMP` | `DATETIME2` |

## 4. Report lifecycle

```
                      ┌──────────────┐
   create report ───► │    OPEN      │ ◄──── withdraw last claim / reject last claim
                      └──┬────────┬──┘
             claim      │        │  owner closes / admin moderates
             submitted  │        │
                  ┌─────▼──────┐ │        ┌──────────────┐
                  │ UNDER_REVIEW│ └───────►│   CLOSED     │ ◄── admin re-opens
                  └─────┬──────┘          └──────────────┘
        admin approves │                    ┌──────────────┐
                        ▼                   │   REJECTED   │ ◄── admin re-opens
                  ┌───────────┐              └──────────────┘
                  │  CLAIMED  │
                  └─────┬─────┘
     admin marks returned│
                        ▼
                  ┌────────────┐
                  │  RETURNED  │  (final - no new claims, no editing)
                  └────────────┘
```

The allowed transitions live in `ItemStatusPolicy` and are unit tested. A report can only be
edited by its owner while it is `OPEN`. A `RETURNED` report is final.

## 5. Matching (FR-06)

`MatchScoringService` is a pure, deterministic unit - no database, no randomness - which
makes it fully unit testable.

| Component | Points | Rule |
| --- | --- | --- |
| Category | 0 / 30 | same category id |
| Keywords | 0 - 30 | `30 x Jaccard(normalised keywords of "title + description")` |
| Location | 0 - 20 | identical location id = 20, otherwise `10 x Jaccard(location name keywords)` |
| Date | 0 - 20 | `max(0, 20 - 2 x days between the event dates)` |
| **Total** | **0 - 100** | capped, bands `HIGH` >= 70, `MEDIUM` >= 40, otherwise `LOW` |

Normalisation: lower case, punctuation removed, stop words removed, tokens shorter than
three characters removed, simple plurals reduced (`keys` -> `key`).

Candidates are the open reports of the opposite type, excluding the report itself and the
reports of the requesting user (a user cannot claim their own item). The service returns at
most ten suggestions, sorted by score.

**Design decision - computed on request:** the PRD explicitly allows "computed on request or
after report changes; choose the simpler reliable approach". Matches are therefore computed
when they are requested and are not stored. This keeps the database free of stale scores and
avoids a background job. The price is that the candidate set is queried per request; with
the indexed status/type columns this is fast for a campus sized data set.

**Product rule:** the response always contains the disclaimer "suggested match only - a
score is not proof of ownership".

## 6. Claims and handover (FR-07, FR-08)

* A claim can only be created for a `FOUND` report whose status is `OPEN` or `UNDER_REVIEW`.
* The owner of a report cannot claim it, and administrators review instead of claiming.
* A second active claim (`PENDING` or `APPROVED`) of the same user for the same report is
  rejected with `409`.
* The claimant sees their own claim, the administrators see all claims, nobody else sees
  anything. The confidential fields are removed from the response, not only hidden.
* The claimant can withdraw a `PENDING` claim. When the last pending claim disappears, the
  report returns to `OPEN`.
* Approving a claim sets the report to `CLAIMED` and rejects competing pending claims with a
  recorded reason.
* Rejecting a claim requires a reason.
* Only an administrator can mark a report as `RETURNED`. An approved claim is required,
  otherwise a documented exception reason must be given. The timestamp and the responsible
  administrator are recorded and the remaining pending claims are closed.

## 7. Security design

### Authentication

Server side session based:

* `POST /api/auth/login` is handled by Spring Security (`UsernamePasswordAuthenticationFilter`),
  which applies session fixation protection, CSRF rotation and the rate limiter.
* The browser keeps the opaque `JSESSIONID` cookie (`HttpOnly`, `SameSite=Lax`, `Secure`
  when `SESSION_COOKIE_SECURE=true`).
* Every state changing request must additionally send the CSRF token in the
  `X-XSRF-TOKEN` header. The token is handed out through the readable `XSRF-TOKEN` cookie
  (double submit). The `CsrfCookieFilter` makes sure the cookie is written on every
  response.

*Why sessions and not a token in `localStorage`?* A token in `localStorage` is readable by
any script that runs on the page. The session cookie is `HttpOnly`, so a cross site scripting
bug cannot read it. The CSRF token in a readable cookie is safe because it is not a
credential on its own - it is only accepted together with the session cookie of the same
origin.

### Authorisation

| Route group | Rule |
| --- | --- |
| `/api/auth/register`, `/api/auth/login`, `/api/auth/csrf` | public |
| `/api/health`, `/actuator/health` | public |
| `/api/admin/**` | `ROLE_ADMIN` |
| `/api/**` | authenticated |
| everything else | static front end |

Ownership rules (edit, close, upload, read private details, claims) are enforced in the
services, and the responses are built from DTOs that physically cannot contain a private
field of somebody else.

### Other measures

* BCrypt password hashing (cost 10), no plaintext password is ever stored or logged.
* Registration always creates the `USER` role - the role in the request body is ignored.
* Safe, non-revealing error messages ("Invalid email or password").
* Upload validation: content type allow list, size limit (5 MB) and magic byte check, so
  executable content cannot be stored under an image name.
* Server generated storage names - the original file name is never used as a path.
* The blob container is private, images are streamed through the authorised endpoint.
* Rate limiting for sign in (per IP and email) and for claim submission (per user and hour).
* Audit events for registration, report creation, moderation, claim decisions and handover.
  The audit metadata never contains secrets.

## 9. Deliberate decisions and limitations

* **Matches are not persisted** - see section 5.
* **Administrators cannot file claims.** This keeps the review free of conflicts of
  interest and is documented in the UI.
* **An item that already has an approved claim (`CLAIMED`) does not accept new claims.**
  The PRD only requires that returned and closed reports accept no claims; being stricter
  protects the handover process.
* **Duplicate claims are prevented in the service layer**, not with a database constraint,
  because a unique constraint on `(item, claimant, status)` would also block a second
  rejected claim for the same report.
* **Guest access is not implemented.** The PRD allows requiring a login for all pages except
  the landing page, which is what this build does.
* **No e-mail notifications, no Entra ID, no Azure Functions, no maps or chat** - these are
  explicitly optional in the PRD and were not started, so that the MVP stays deliverable.
